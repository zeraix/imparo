AdaSpark: Adaptive DSpark with Online Learning
for Tree Verification and N‑gram Fill

Liquan Liu  ·  Yifan Zhang

Zeraix · liquan@zeraix.com, fergus@zeraix.com

28 September 2026

Abstract

Block drafters such as DSpark propose ranked candidates for several positions in one forward pass, and a tree verifier checks them in one pass of the target. The number of rows to verify trades the tokens a wider tree is expected to accept against the time a wider verify takes. Most existing schedulers that choose this number take the verify time from a table or model measured before serving, corrected online by at most one scale factor, and take acceptance from the drafter's own confidence estimates or from a map fitted offline.

AdaSpark learns both quantities while it serves, with no profile, calibration or sweep in advance. It learns which verify widths are worth offering and fits the verify time of each as a function of context. It fits the probability that each candidate is accepted to the target's verify outcomes, with the drafter's confidence head as one input, and orders and sizes the tree by that fitted probability instead of by the head's. The same model prices n-gram continuations of the request's own text, so drafted and text-derived candidates compete for rows in one best-first order. The width is chosen by pricing time at the long-run decode rate.

On multi-turn conversations from six public datasets, on three dense targets and one mixture-of-experts target, AdaSpark decodes 1.5–2.9× faster than llama.cpp's DSpark with the same drafters, which on three of the targets is slower than llama.cpp's own autoregressive decode; on one engine, the scheduler alone contributes 1.17–1.53×. Without a width sweep, its width is within 1.1% of the best fixed tree width that an offline sweep finds for each dense target and context, and on the mixture-of-experts target, where it learns widths between the swept ones, it is faster than every fixed width.

1 Introduction

Speculative decoding [4, 5] drafts tokens cheaply and verifies them in one forward pass of the target model, keeping the longest prefix the target agrees with. Drafters that emit a tree of candidates rather than a single chain raise the number of tokens accepted per pass [6, 7, 18, 35, 36]. Block drafters such as DSpark [3] produce a whole block of positions from one forward pass of a parallel backbone, each position with a ranked list of alternatives, so a tree built from one block can be as wide as the scheduler allows [41, 42]. The scheduler must decide how many rows to verify.

That decision needs two quantities: the number of tokens a tree of n rows is expected to accept, and the time a verify of n rows takes. Many schedulers fix the budget by hand or by a sweep [42, 43, 45]; others learn a chain length online without modelling the cost [2, 13, 54], or measure a few lengths in short trial phases [48]. Those that price the verify read its time from a table, curve or model measured before serving: a profile taken at engine start [3, 37, 39], a table written by an offline profiler [38], a latency ladder measured once per deployment [41], or a roofline model calibrated offline, with at most one online correction factor [40]. The two open-source serving engines that implement this drafter's scheduler both take their table at one context length or one short range of contexts (§7). Acceptance is taken from the drafter's probabilities [39, 40], its trained confidence head [3, 12], or a map fitted offline to the target's outcomes [41, 46]. Most of these schedulers already choose the size anew for every verify; what separates them is where the cost and the acceptance come from (Table 13).

We measure the verify time on four targets (§3.2). It is a step function of n, as reported before for GPU tile allocation [3, 40] and for llama.cpp's Metal backend [51], and the steps fall in different places for 8-bit and 4-bit weights. On a mixture-of-experts target it rises with every row, because each row is routed to its own experts [39, 48, 49]. It also grows with context, faster for a wide verify than for a narrow one. The best fixed width therefore differs between targets and contexts (§3.4). On the acceptance side, a model fitted to the target's own outcomes predicts acceptance better than the drafter's confidence head, as TreeSpark [41] found for a map fitted offline (§3.3).

AdaSpark is a scheduler for DSpark tree verification that learns both quantities while it serves. It learns which verify widths are worth offering and fits the verify time of each as a function of context, fits an acceptance model to the target's outcomes, lets n-gram continuations of the request compete with the drafter's candidates for rows, and chooses each round's width from the two fitted models. It needs no cost profile, no calibration and no width sweep taken before serving, and it comes within 1.1% of each dense target's best fixed width on its own, running 16 rows on one and 8 on the others in most rounds; on the mixture-of-experts target it moves between widths of 2 to 8 rows from round to round, which no fixed width can do, and is faster than every fixed width. Its constants (Appendix C) were set once, on one target and a separate development corpus, and are used unchanged on all four.

Contributions.

  1. An online verify-cost model that learns which widths to offer, measuring a new width only where it could change the choice, and prices each as a function of context with a low-quantile loss, with no offline profile or calibration; each width's law keeps a bank of samples per context band, so it fits every context it has seen although contexts arrive one request at a time (§3.2).
  2. An acceptance model fitted online to the target's outcomes: a multinomial over each parent's children that takes the drafter's confidence head as one input and replaces the head's estimate in ordering and sizing the tree, with separate terms for n-gram candidates and for the evidence each source gives about the other (§3.3).
  3. N-gram candidates priced by the same model as the drafter's. Earlier methods that verify model-drafted and retrieved candidates in one tree divide the rows by fixed rules [43, 44]; here the two sources compete for rows in one best-first order. Under the model, at a fixed width they cannot lower the expected tokens of a verify, and they widen it only when the cost model says they pay for it (§3.3).
  4. A width rule for step-shaped, non-monotone costs that prices time at the long-run decode rate rather than at each round's own ratio, with the conditions under which it is optimal (§3.4); end to end it ties the per-round ratio and widens trees at long context. Starting with nothing learned and with no sweep or calibration taken before serving, it comes within 1.1% of the best fixed width on each dense target and is faster than every fixed width on the routed one (§3.4, §5.5).

We test these claims against llama.cpp's DSpark with the same drafter files, on three dense targets and one mixture-of-experts target, on multi-turn conversations taken from six public datasets by a fixed rule, with every reply generated to its end or to the 8,192-token cap, and every exclusion counted (§4). An ablation adds one mechanism at a time, and the gain over llama.cpp is split into the part the engine gives any algorithm and the part the scheduler adds (§5).

2 Background

2.1 DSpark drafters

A DSpark drafter [3] is a small network that reads hidden states from selected layers of the target and proposes tokens for the B positions after the last committed token, the anchor. A parallel backbone produces logits for all B positions in one forward pass; a lightweight sequential head (the Markov head) then adds to each position's logits a low-rank bias from the token chosen at the position before, left to right. A confidence head predicts, per position, the probability that the draft token survives verification given that the tokens before it did; in [3] it is trained on the acceptance rate of speculative sampling at temperature 1 and calibrated offline.

2.2 Tree verification

A verify round takes a tree of candidate tokens rooted at the anchor and runs the target once over all its nodes. Each node attends to the committed context and to its own ancestors. A verify of width n has n rows: the anchor and n − 1 candidates. Under greedy decoding a candidate is accepted when its token equals the target's argmax at its parent's row. At most one child of an accepted node can match, so the accepted nodes form a single path from the anchor. The round commits that path and the target's argmax at the path's last node. A chain is the special case of a tree with one child per node.

At each position we keep the drafter's top K = 8 candidates: the top one is the drafter's pick, the other K − 1 its siblings. The candidates of one block form a tree of a fixed shape (Figure 1). The picks form a spine: the pick at position i hangs from the pick at position i − 1, and the first from the anchor. The siblings at position i hang from the same parent as the pick and are leaves: our engine runs the Markov head along the picks only, so it scores nothing below a sibling, and an accepted sibling ends the drafter's contribution to the round. Running the head once more for each expanded parent gives siblings children of their own, as PCTree [42] and TreeSpark [41] do; we did not implement it. N-gram candidates (§3.3) form chains that branch from the anchor and from each pick, and can run past the end of the drafter's block.

3 AdaSpark

3.1 Overview

Figure 2 shows one round and Algorithm 1 states it. The drafter emits a block with its top-K candidates per position, and n-gram chains from the request's own text are added to them. Each candidate gets q, the probability that it is accepted if its parent is. The candidates are ordered best-first by Q, the product of q along the path from the anchor, so that every prefix of the order is itself a tree. The width chooser takes the prefix length that maximises Eq. (7), the target verifies that prefix in one forward, and the round's measured time and accept outcomes update the two online models.

One order serves every width. A node can be accepted only if its parent is, and at most one child of an accepted node is accepted. The probability that candidate j lies on the accepted path is therefore Qj, and the expected number of accepted candidates of a tree is the sum of Q over its nodes,

S(n)  =  Σj ∈ first n−1 nodes of O  Qj,   Qj = ∏i ∈ path(j) qi
(1)

Proposition 1. Fix the round's q for every candidate before the tree is chosen, and index the candidates so that every parent precedes its children. Order the candidates by decreasing Q, breaking ties toward the lower index. Then for every n, the first n − 1 candidates of the order form a tree, and no tree of n − 1 candidates has a larger S under the model.

Proof. Since q ≤ 1, a child's Q is at most its parent's, and the parent has the lower index, so the tie rule places it first as well. Every candidate's parent therefore precedes it in the order, and every prefix is closed under taking parents, that is, a tree. The prefix consists of the n − 1 largest values of Q, so its sum is at least that of any other set of n − 1 candidates, trees included.

This is the node-selection rule of dynamic-tree drafters such as EAGLE-2 [35] and OPT-Tree [36], and schedulers for block drafters and for mixture-of-experts targets already use its prefix property to choose a tree size each round [39, 40, 41]; we state it because the chooser depends on that property at every width at once. The width decision reduces to choosing a prefix length, and one pass over the order gives S(n) for every n. The engine computes each q once per round over all of a parent's candidates, placed in the tree or not (Eq. 6), which is what the proposition requires. The optimality is under the model's q; how well that matches the target's outcomes is measured in §5.7.

3.2 Online verify-cost model

What a verify costs. A verify of n rows streams every weight of the target from memory at least once, whatever n is, and multiplies n rows of activations by each weight matrix. The first cost is why speculation pays: sixteen rows stream the same weights as one. The second is not linear in n on a GPU. For a few rows the engine runs dedicated row kernels that read each weight once for all the rows, up to a limit that depends on the weight format. Above that limit a matrix kernel computes whole tiles: at n rows it runs one geometry g(n) from a small set, pads n up to that geometry's row count κ(g), and may walk the weights more than once. The engine's per-device tuner picks the geometry for each n by measured speed. Qualitatively,

T(n, c)  ≈  W(g(n))  +  γ · κ(g(n))  +  Att(n, c)
(2)

where W(g) is the time to stream the weights under geometry g, γ the matrix time of one padded row, and Att the attention over a context of c tokens. W and κ are constant on intervals of n, so T is nearly flat inside each interval and steps between them. Nothing makes the steps monotone: the tuner ranks geometries by speed at the widths it measures, and a geometry that is fastest for a full tile can be slower for a padded one. We call each interval of n that runs one geometry a row class. Steps of this kind have been reported for CUDA tile allocation [3, 40] and, on an Apple laptop of the same generation as ours, for llama.cpp's Metal kernels, where a 9-token verify was cheaper than a 7-token one because a matrix-matrix kernel replaced per-position matrix-vector products [51].

On a mixture-of-experts layer each row is routed to its own experts, so a verify of n rows streams up to n times the expert weights of one row. W then depends on n itself, and time rises inside a class as well as between classes. This is the cost that earlier work on speculative decoding for mixture-of-experts targets models by the number of distinct experts a verify touches [39, 48, 49, 50]. That number is bounded by the expert count, so the expert traffic must level off once the rows together touch most experts; our routed target has 32 experts with 4 per row. We did not separate expert traffic from the matrix kernels' own steps; the verify time kept rising up to 32 rows, the widest we measured (Table 1).

Measured verify time. We ran DSpark decoding with the tree width pinned at each n and took the median verify time over the rounds that verified exactly n rows, dropping the first two rounds, at three contexts (443, 1,596 and 8,444 tokens), in two passes of opposite order. The prompts continue public text (§4.3). Figure 3 shows the result for all four targets.

The dense targets show the steps of Eq. (2), and the steps sit in different places. On LFM2.5‑2.6B, whose weights are Q8_0 (8-bit), a verify of 16 rows costs 11% more than a verify of 2 rows at a 1,596-token context, and a verify of 20 rows 40% more than one of 16. Further out the curve is not monotone: a 48-row verify, which runs a different geometry from a 40-row one, is 4.3% cheaper than it. On Qwen3‑4B, whose weights are Q4_K_M (mostly 4-bit), the verify is flat to 8 rows and then steps steeply: at a 1,596-token context a 10-row verify costs 1.48 times an 8-row verify, and a 20-row verify 2.07 times a 16-row one. Qwen3‑8B, also Q4_K_M, has the same steps: 1.51 and 2.14 times. The 4-bit matrix kernel processes the rows in fragments of 8: up to 8 rows run in one fragment, close to the memory bandwidth, and from 9 rows in two fragments that reach about two thirds of that throughput. On the routed target time rises with every row, because every row is routed to its own four experts: 8 rows cost 1.64 times as much as 2 rows, and 16 rows 2.16 times.

Context dependence. A verify also gets slower as the conversation gets longer, because every verified row attends over every earlier token, and a wide verify gets slower faster. On Qwen3‑4B, where every layer attends, a 16-row verify gains 2.4 ms per 1,000 tokens of context and an 8-row verify 1.3 ms, so the extra 8 rows cost 12 ms at 443 tokens and 21 ms at 8,444. On the two LFM2.5 targets most layers are short convolutions and only a few attend, and the 8- and 16-row classes gain at most 0.2 ms per 1,000 tokens and the 32-row class under 0.45 ms. One constant per class is therefore not enough. Fitting

Tk(c)  =  αk + βk · c
(3)

per class k over the three contexts gives the intercepts and slopes of Table 1. The intercept αk is the part that does not depend on context: the weight pass and the tile steps. The slope βk is the extra time per token of context, the attention pass, and it grows with the class's row count. A slope shared by all classes therefore under-prices the wide classes at long context, which is where the ranking of widths changes.

The model. The cost model answers one query: the time a verify of the offered width of class k takes at context c. It is fitted from the verifies the engine runs, so measurement costs no extra work.

Which widths are offered. The model does not take the widths from the backend; it learns them. It starts from a ladder of 2, 4, 8, 16, 32 and 64 rows and treats the widths between two neighbours as one class, priced at its top width, the only width in it the chooser is offered. It then splits a class only where a width inside it could change the choice. Between two measured widths a < b, a width inside is taken to cost at least T(a) and to accept at most what b − 1 rows accept, which the round already knows; if even b − 1 rows at T(a) cannot clear the chooser's switching margin against the width it holds, nothing inside is measured. Once the chooser has held a width for 8 rounds, the nearest class that passes this test is split, beside the held width when its time rises by more than 25% and at its midpoint otherwise, and the new width is measured three times. At most 24 widths are learned. A measurement round asking for more rows than any tree the drafter can offer teaches the table its reach (57 rows for the Qwen3 drafters). A step down inside a class, like the 48-row verify above, is found only if a split lands on it. The alternative is to take the classes from the backend's matrix kernels. On this engine only the 8-bit kernel has such a partition, one class every 8 rows plus the tile boundaries of Eq. (2), so the 4-bit and routed targets would borrow a partition that is not theirs. Proposition 2. Let T be constant on each class, let Sd and Sng be non-decreasing in n, and let gd, gn ≥ 0. Then some maximiser of V in Eq. (7) (§3.4 defines its terms) is the top width of a class.

Proof. Inside a class T does not change, and with non-negative gains the tokens term cannot fall as n grows, so moving any width to the top of its class never lowers V.

The gains are clamped to [0.25, 4] (§3.4), so the condition on them always holds. When a wider class is cheaper than a narrower one, as at the 48-row inversion above, each width is priced at the cheapest class whose top is at least that width, and the narrower, dearer class is never chosen. A running maximum over narrower classes, which vLLM uses to make its table monotone (§7), does the opposite: it raises the cheaper wide class to the narrower class's price. A stopping rule that grows the tree until the estimated speedup first falls, as in [40], assumes a convex cost and can stop below a cheaper wide class. The idea of Proposition 2 appears in SGLang's DSpark scheduler as an option that fills a verify up to the CUDA-graph size its forward is padded to anyway [38].

The context law. Interference is one-sided: a busy GPU, a cold pipeline or a thermal limit makes a verify slower, and nothing makes it faster than the machine can run it. We therefore fit a low quantile rather than the mean. For each class the model regresses the verify time yt, normalised by the class's scale (the lowest of its first three measured times), on a basis in the context, u = c/8192:

minθ Σt ℓτ( yt − θ⊤φ(ut) ) + λ1‖θ‖1 + λ2‖θ‖22,  φ(u) = [1, u, u2, √u, ln(1+u)],  ℓτ(v) = v(τ − 1[v < 0])
(4)

Proposition 3. Let an observed verify time be Y = t + ε, where t is the machine's time for the verify and ε ≥ 0 is interference with P(ε = 0) = π. For every 0 < τ < π the τ-quantile of Y is t, while its mean is t + E[ε].

Proof. P(Y < t) = 0 < τ and P(Y ≤ t) = π > τ, so t is the unique τ-quantile.

A least-squares fit therefore absorbs every burst of interference into the price, and a low quantile does not. We set τ = 0.15 by hand; by Proposition 3 it recovers the machine's time as long as more than 15% of rounds run free of interference. Real timings also carry a small two-sided jitter, which makes the fitted quantile slightly low. The quantile loss is that of Koenker and Bassett [20]. The context coefficients are constrained to be non-negative, so the fitted time never falls as context grows. The basis is redundant on purpose: an affine law fits the dense targets, but other attention routes can add curvature past some context length. The penalty is an elastic net [21] rather than a lasso because over a short run the context barely moves and the basis terms are nearly collinear; the L2 term keeps the weight shared instead of letting it jump between them. The solver is FTRL-Proximal [19], with the per-coordinate learning rate floored so the law can follow a machine that drifts. The online pass alone does not fit the shape. Contexts arrive one request at a time, each sample moves the intercept toward the current context, and only the contrasts between requests teach the slope: on Qwen3‑4B the online 8-row law priced 28.9, 29.8 and 35.0 ms at 443, 1,596 and 8,444 tokens, where the verify's 15th percentile was 25.2, 26.7 and 35.3 ms. Each law therefore keeps a bank of the newest 16 samples of every context band (the bit length of the context), stored with the law together with its weights and FTRL's accumulated squared gradients, so that a restored law learns at the rate it had reached, and at the end of each request a batch refit over the bank, the bands interleaved, replaces the online law if it predicts the newest quarter of every band better; on the same samples it prices 25.6, 26.7 and 35.0 ms. A misfit law does little harm to the class that is running, whose level (below) corrects it within 8 rounds; it misleads the choice through the classes that are not running, which are the neighbours the chooser weighs against the running one. The penalty weights are λ1 = 0.002 and λ2 = 0.01 on the normalised time. The fitted law is clamped to between 0.5 and 3 times the class's lowest observed time.

The price. The price the chooser reads for class k is the product of three terms, each on its own timescale:

T(nk, c)  =  lawk(c)  ·  levelk  ·  Dnow / Dk
(5)

The law is the fit of Eq. (4), a property of the kernels that changes slowly. The level is the minimum, over the class's last 8 verifies, of the measured time divided by the law's value, clamped to [0.5, 2]. It follows the machine within 8 rounds of the class running, and unlike a minimum over all time it rises again when the machine slows. The last factor corrects for staleness. Only the chosen class runs in a round, so every other class was last measured earlier, possibly on a quieter machine, and would look cheaper than it is. The round's fixed cost D, the drafter's forward and the tree build, runs in every round whatever the width, so it serves as a clock: each class records D when it is measured, and its price is scaled by the ratio of the current D to that value. Until a class's law has enough samples, its price is its lowest measured time, scaled by the same clock. The first round of a request is not learned from. On all four targets it runs cold: its verify takes 5–11% longer than that width's typical time and its drafter 3–7% longer, and the second round is within 0.3%. As the first sample of an empty level window it would price the width it ran high enough to drop out of the offer, and that width would not run again to correct it. Pricing a width takes about 11 ns of host time and a training step, bank included, about 44 ns, so with 24 widths a round spends under 0.4 µs in the cost model; the refit at the end of a request takes about 0.03 ms per law.

Cold start. A width with fewer than three measurements is measured by running rounds at it, three per width, narrowest first. These rounds still decode. The ladder's six widths take 18 rounds and each later split three more; a round whose tree comes out narrower than the width it measures does not count. From an empty store, the first request on the four targets spends 34 to 49 rounds measuring, 6–9% of its decode time, and the whole instrumented run 49 to 61 rounds, under 4% of its rounds (§5.6). The table is stored, so a restart does not measure again: the measured runs of Table 11, which start from a stored table, spent 0 to 1.3 rounds per run measuring a new width.

3.3 Acceptance model and n-gram candidates

Two quantities available at draft time predict whether a candidate will be accepted. The confidence head is a scalar from a small network trained offline to predict acceptance. The pick's share is its softmax mass among the drafter's top K at that position, computed from the logits of the same forward. The head is calibrated on average over its training distribution. The share reports how peaked the drafter's distribution is at this position, which separates a determined continuation, such as a closing bracket or the rest of an identifier, from an open one. Where the two disagree the share is the better guide: on LFM2.5‑2.6B, over the held-out prompts of the development corpus (§4.3), picks with head 0.34 and share 0.94 were accepted 75% of the time, and picks with head 0.70 and share 0.43, 40% of the time. The model below uses both, and Table 2 measures on every target how much better it predicts acceptance than the head-based estimate it replaces.

The head in [3] is trained on the acceptance rate of speculative sampling at temperature 1, while we decode greedily, where a candidate is accepted only if it equals the target's argmax; part of the head's loss may come from that mismatch rather than from the head itself. And fitting acceptance to the target's outcomes is not new: TreeSpark [41] fits a two-parameter map from the drafter's probability to acceptance on DSpark trees, and TAPS [46] trains a scorer that is a softmax over each parent's children, both offline. The model here is fitted online, per deployment, from an empty store, and carries terms for the n-gram source.

N-gram candidates. AdaSpark adds n-gram fill to the drafter's tree: continuations of the request's own text. It keeps an index of that text, prompt and reply, keyed by suffix. From the anchor and from each of the drafter's picks it follows a chain: the token that followed an earlier occurrence of the current context, read on along the earlier passage, or else the most frequent follower of the last three tokens. A chain step equal to a candidate the drafter already proposed marks that candidate as agreed; otherwise it adds a new n-gram node. Chains stop 32 tokens below the anchor, which is past the drafter's block, or when nothing is proposed. The n-gram nodes enter the same best-first order as the drafter's, priced by the n-gram terms of Eq. (6) below.

Form. At most one child of an accepted parent can be the target's argmax, so the candidates of one parent and an explicit none outcome share one softmax:

qj = P(j accepted | parent accepted) = exp(sj) / (1 + Σi ∈ cand(parent) exp(si)) pick  s = a0 + a1·logit h + a2·logit σ + ψ + breq sibling s = a3 + a4·log r + a5·logit h + a6·logit σ + ψ + breq n-gram s = logit psrc + wbucket + ψ + breq
(6)

Here h is the confidence head at the position, σ the pick's share, r a sibling's share of the siblings' total, ψ the context term (and, for drafter candidates, a depth term), breq a per-request intercept, and psrc the n-gram source's measured top-1 precision on the committed text. A bucket indexes an n-gram candidate's evidence (the length of the copy it continues, or its follower count), its kind, and the number of n-gram nodes above it on its path. Two further terms connect the sources. A candidate both sources propose (agreed) keeps its drafter score and adds max(0, logit psrc) and its bucket's weight. A drafter candidate whose parent also has a different n-gram proposal (contradicted) subtracts max(0, logit psrc) and adds its own bucket's weight. The sum in the denominator runs over every candidate of the parent, placed in the tree or not, so each q is fixed for the round before the tree is chosen.

Why the n-gram needs its own terms. An n-gram node has neither a head nor a share, and whether it is accepted depends on whether the text repeats, which the drafter's features do not see. With one intercept shared by both sources, the maximum-likelihood fit sets the average predicted probability equal to the average outcome over the nodes of both sources together; a source whose base rate differs from the pooled rate is then mispriced by the difference, in opposite directions for the two sources. With a term per source, each source's average holds separately. The two sources also carry evidence about each other, which is what the agreed and contradicted terms price. For an agreed node, agreement multiplies the odds by P(agree | correct) / P(agree | wrong) = p/((1 − p)c), where c ≤ 1 is the chance that a wrong follower lands on this very candidate; logit p is the lower bound of its logarithm, and the floor at zero keeps a weak source from counting against a token it agrees with. §3.6 lists what the two terms corrected when they were added.

Learning. With an empty store the drafter's seven coefficients start from a prior derived from the features' definitions rather than from an offline fit: the pick scores ln 2 + logit h, a sibling scores log r, and both share coefficients start at zero. Every bucket weight starts at zero. Each coefficient is updated online by FTRL-Proximal on its deviation from the prior, and leaves the prior only once its accumulated gradient exceeds 3√m after m updates; the request intercept adapts by AdaGrad [70]. After each round every candidate of every accepted parent is labelled, whether or not it was placed, so a round teaches the model about nodes it did not verify as long as their parent was accepted. The model competes with the estimate it replaces, the head corrected by a per-request logit offset. A guard scores each round's labels under both before either learns from them, and the fitted model prices the tree only while its decayed log loss is the lower. The coefficients persist across requests; the offset and the intercept restart with each request.

Exploration. Every drafter candidate of an accepted parent is labelled, so the drafter's terms need no exploration. An n-gram bucket can go unlabelled: its candidates hang below other n-gram nodes, and a bucket priced too low is never placed and so never corrected. Every 16th tree round that has n-gram candidates, the last row goes to the n-gram frontier node of the bucket with the fewest labels.

Corollary 4. At every width n, the first n − 1 nodes of the merged order have at least the S of any tree of n − 1 drafter candidates, under the round's q, and the verify has the same width.

Proof. Every tree of drafter candidates is a tree of the merged set, so Proposition 1 applied to the merged set bounds it.

The comparison is under the round's q, which already counts the n-gram candidates in each parent's softmax. It says that, given the model, adding n-gram candidates never makes a verify of a given width worse: at a fixed width they take rows only from drafter candidates they outrank, and the verify's time, which depends on the width, is unchanged. The chooser can also move to a wider class because of them, when their expected tokens, scaled by their own gain gn (§3.4), pay for the step. Table 9 counts how often each case occurs on each target. Graft [43] measured this failure: with a fixed split of a 60-node budget, retrieved candidates attached at the root displaced strong draft nodes and made decoding slower than the drafter's tree alone (3.62× against 3.73× on average over five benchmarks, as reported in [43]), which Graft [43] avoids by pruning the drafter's tree first and filling only the freed slots.

3.4 Choosing the width

For each offered width n the chooser forms the round's expected tokens, 1 + S(n), and its expected time, D + T(n, c). Maximising their ratio is the objective of prior cost-aware schedulers [1, 39, 40, 52], of DSpark's own scheduler [3], and of the DSpark schedulers in vLLM and SGLang (§7). AdaSpark instead maximises

V(n)  =  1 + S(n0) + gd·ΔSd(n) + gn·ΔSng(n)  −  ρm·( D + T(n, c) )
(7)

where n0 is a fixed reference width of 8 rows, so that learning a narrower width does not move the point the marginal is measured from, ΔSd and ΔSng are the expected tokens that the drafter's and the n-gram's nodes add above n0, and ρm is the long-run decode rate of the context band m the round is in. It differs from the ratio in three ways.

(i) Time is priced at the long-run rate. The quantity to optimise is the time to decode a reply, not the ratio of any one round.

Proposition 5. Split a reply's positions into context bands, band m holding Nm positions. Assume that within a band the round states are independent draws from a distribution that does not depend on the width rule, that the mean round time is positive, and that the reply's text does not depend on the rule. Then, as Nm grows, a width rule minimises the band's expected decode time if and only if, for almost every state, it maximises E[A − ρm*C | state], where A is a round's committed tokens, C its time, and ρm* the band's best achievable rate.

Proof. By the renewal-reward theorem the long-run rate of a rule in band m is Rm = E[A]/E[C], and the band's decode time divided by Nm tends to 1/Rm. The text, and so each Nm, is fixed, so the reply's time is minimised by maximising each Rm. By Dinkelbach's theorem [31], max E[A]/E[C] = ρ* exactly when max E[A − ρ*C] = 0. With the state distribution fixed, E[A − ρ*C] is the average over states of the conditional expectation, which is maximal if and only if the conditional expectation is maximal for almost every state.

The independence assumption is an approximation: the width a round takes decides where the next round starts, and so what the drafter proposes next. The text assumption holds because decoding is greedy and, within the widths one accumulation order serves, a verify's rows do not depend on its width (§3.5); the rounds that ran wider, up to 4% of them, can change the text only at a near tie (Table 12 counts how often the text differs between arms). The per-round ratio is not this rule. Comparing a narrow width with a wide one, the ratio takes the wide one when its marginal tokens per unit time exceed the round's own ratio; the rule of Proposition 5 takes it when they exceed ρm*. In a round better than its band, the ratio refuses rows worth buying; in a worse round it buys rows that are not. AdaSpark uses the band's achieved rate in place of ρm*: committed tokens over time, both decayed with a half-life of 64 rounds. This is a stochastic form of Dinkelbach's iteration, in which the rate the rule achieves becomes the price it uses next. The same renewal-reward argument has been used to choose a chain's draft length under network delay [54]; here it is applied to the tree width, over a cost with steps. A band is the set of contexts with the same bit length (128–255 tokens, 256–511, and so on), and until a band holds 8 rounds the chooser uses the per-round ratio. D is the same for every width, so in Eq. (7) it shifts every width's value equally; it enters the choice through ρm, which is measured over whole rounds, and through the ratio used before ρm is known. On LFM2.5‑2.6B, on 16 held-out development prompts (§4.3) in two interleaved passes, pricing at ρm instead of the per-round ratio changed milliseconds per token by −0.39% (standard error 0.46%), a tie, and raised the mean width from 8.0–8.1 rows to 8.2–12.7 rows on the prompts with 4k–16k tokens of context, where the two rules disagree most.

(ii) The marginal is rescaled. S is a sum of per-node probabilities and a poor estimate of what extra rows buy. On LFM2.5‑2.6B the realised gain of 16 rows over 8 was 1.69 times the predicted gain at a 1,596-token context and 0.885 times at 8,444: errors in opposite directions, which no single constant corrects. The gains gd and gn, one per source, are therefore fitted as lines in context by ridge-regularised least squares of realised on predicted marginal, shrunk toward 1 and clamped to [0.25, 4]. The observations come without extra rounds: by Proposition 1 and the width invariance of §3.5, the accepted path of a round that ran wider than n0 also gives what the n0-row prefix would have accepted. Only rounds wider than n0 teach the gain, so the chooser's first incumbent is the widest offered width; widths below n0 are priced with the unscaled marginal.

(iii) Hysteresis. The chooser keeps its current width unless another beats it by a margin. Once ρm is known, the alternative's V must exceed the incumbent's by 0.04 times the incumbent's expected tokens; before that, the alternative's ratio must be 4% higher. The margin was set on LFM2.5‑2.6B as the smallest tested value at which the choice no longer flipped on noise; at about 0.05 and above it never left its incumbent.

No fixed width fits every target. Table 3 compares fixed tree widths of 8, 12 and 16 rows, the drafter's block verified as a chain, and AdaSpark's chosen width, at the three contexts on all four targets. Every arm (§4.4) uses the fitted acceptance model and no n-gram candidates, so the arms differ only in how the width is set, and every measured run starts from a copy of its store, so no arm learns from another. The best fixed width changes with the target and the context, and only a sweep like this one finds it. AdaSpark's width needs no sweep. On the three dense targets it is within 1.1% of the best fixed width in every cell and faster in seven of the nine. On the routed target it is faster than every fixed width, by 2.4%, 4.2% and 0.6% at the three contexts, because it learns widths between the swept ones and moves between them from round to round (§5.5). Figure 5 shows why the targets differ: going from 8 to 16 rows buys about 11% more tokens per round on both LFM2.5 targets (medians 11.1% and 10.9%), but costs 5.7% more time per round on the dense target and 28.1% on the routed one.

3.5 What the verify guarantees

AdaSpark decodes greedily: every emitted token is the target's argmax on the verify row for exactly the emitted prefix. Two stronger properties were tested. A tree node whose ancestors are a chain's rows computes that chain row bit for bit, so a tree never changes a token a chain verify would have produced. And within one accumulation order of the matrix kernels a verify's rows do not depend on its width: we compared every prefix of a verify of up to 64 rows with the same rows verified alone, on all four targets. Rows are bit-identical among widths 3 to 16 on the three 4-bit targets and 3 to 24 on the 8-bit one; these ranges span several row classes, and a wider verify accumulates in another order, so its rows differ by rounding, and 2 rows run a different kernel altogether. The chooser's widths fell inside these ranges in 96.1%, 90.4%, 99.6% and 99.5% of rounds on LFM2.5‑2.6B, LFM2.5‑8B‑A1B, Qwen3‑4B and Qwen3‑8B (Figure 8); the rest were wider verifies and, on the routed target, 2-row verifies (8.5% of its rounds). A property that does not hold is equality with one-token decode. A batched verify runs multi-row matrix kernels whose accumulation order differs from the one-row kernel's, so on a near tie its argmax can differ from plain decode's. Making the verify reproduce one-token decode is possible and was measured: it costs 2.2% of decode speed on LFM2.5‑2.6B and 5.0% on Qwen3‑4B if decode moves to the verify's kernels, or 25–70% of verify time on 8-bit weights at 3 to 8 rows if the verify moves to decode's. We keep the fast kernels and report how often the text differs (§5.7).

4 Experimental setup

4.1 Drafters and baseline

Appendix A describes the engine, the machine, and the targets and drafters (Table 15). The Qwen3 DSpark releases are training checkpoints: their files declare the architecture dspark with the checkpoint's tensor names, and neither engine loads them as released. We convert them to the tensor layout both engines' DSpark loaders read (named dflash in their sources) and quantise them with the same quantiser as the target.

The baseline is llama.cpp [34] (Appendix A) with --spec-type draft-dspark and the same drafter file, at its defaults: at most three draft tokens per round (--spec-draft-n-max 3) and no minimum draft probability (--spec-draft-p-min 0). Its verification is a chain. Both engines run with a 32,768-token context and serve one request at a time.

4.2 Test set

Every prompt in the end-to-end evaluation comes from a published dataset; we wrote no prompt text. The protocol is ours: multi-turn conversations over each engine's HTTP API, with each engine's own replies carried as history. A method that learns from its workload is easy to favour with a workload chosen for it, so the text is fixed by the rule below and can be rebuilt by anyone.

Selection. Items are taken in each dataset's own order: the first that pass one length cap (4,000 characters of prompt, 12,000 for the three sources that carry a document). The benchmark sets take a category's items until the category holds at least two turns, so a multi-turn item can take it to three. The single-category sets take their first eight conversations that pass the dataset's own filters (for WildChat: English, not flagged toxic, not redacted, at least four user turns). There is no sampling, and no item was examined for how any engine performs on it. SPEED-Bench's qualitative split reuses some Spec-Bench questions and repeats some of its own first turns; the rule keeps every copy it selects, and two conversations of the evaluation subset (humanities and QA) open with the same question as a Spec-Bench conversation. AdaSpark's n-gram index holds only the current request's text, so a repeated question gains nothing from an earlier copy. The conversations' text was fixed and committed before the first end-to-end run; a conversation's hash covers its turns, and ToolACE's tool schemas are converted by the rule in Table 5. Each conversation records its source row identifier and a hash of its text, and each file records the source revision it was built from; rebuilding the set six days after the first build reproduced all 73 hashes.

Evaluation subset. Replies with reasoning average about 2,000 tokens, so one pass of one arm over all 148 turns takes over an hour on the smallest target and many hours on the largest. The end-to-end runs therefore use a subset fixed by rule before any run: the first conversation of every category of a multi-category source, and the first half of the conversations of a single-category source. It keeps every category, 42 conversations and 87 of the 148 turns (Table 5); a tool turn gives two timed replies, so the subset has 95. The other 31 conversations and 61 turns were then run with llama.cpp's DSpark and AdaSpark as a held-out check (§5.1).

Departures from the sources' protocols. Replies run to their end, up to 8,192 tokens, rather than to Spec-Bench's cap of 1,024, because a reasoning model's reply would be cut inside its reasoning at that length. Decoding is greedy, which this verifier requires. Under greedy decoding a reasoning model occasionally repeats itself until the cap; Qwen3's documentation warns of this for its reasoning mode. Such a loop is trivially predictable text that favours every speculative method, so a reply that reaches the cap in any arm is left out of every speed ratio and counted separately. Reasoning is on for every target: LFM2.5's chat template has no switch for it, and Qwen3 is run with it on. A tool turn gives two timed replies, the call and the answer after the recorded result is returned; when the model answers without calling, the second reply does not run.

4.3 Microbenchmark and development prompts

The measurements of §3.2 and §3.4 continue text at a fixed context rather than hold a conversation: a prompt is token ids with no chat template, at 443, 1,596 or 8,444 tokens. The text is LongBench's government reports, news articles and source code, taken whole in the data file's order until the context is reached and then cut to its first tokens, one prompt set per vocabulary. No text is repeated, since repeated text is trivially predictable and would favour every drafter.

Development corpus. The constants of §3 and the design comparisons of §3.3, §3.4 and §3.6 used a separate corpus of 489 prompts from 17 public suites: HumanEval, GSM8K, Alpaca, MT-Bench, Natural Questions, CNN/DailyMail and Alpaca-zh at contexts of 128 to 2,048 tokens, and ten LongBench subsets at 1,024 to 16,384 tokens. It is split by suite and context band into 408 prompts for fitting and 81 held out, and a 16-prompt subset takes two held-out prompts per context band. Long items are cut from the middle and short ones reach a long band by packing distinct items; no text is repeated. The corpus shares two sources with the test set, MT-Bench (inside Spec-Bench) and LongBench; we did not check the two for shared items.

4.4 Arms and metrics

Each speculative arm serves the evaluation subset in the order of Table 5 on one server. Every imparo arm starts from an empty learned store and learns only from its own requests, so its models see the workload change five times. Two arms separate the engine from the scheduler: imparo runs DSpark in llama.cpp's configuration, so comparing the two engines holds the algorithm fixed, and comparing that arm with AdaSpark holds the engine fixed. The arms are:

  • autoregressive, in each engine: no drafter.
  • llama.cpp DSpark: the baseline of §4.1, a chain of at most three draft tokens per round.
  • imparo DSpark: the same configuration in imparo: a chain of at most three of the drafter's picks, no minimum probability, no tree, no learned models, no n-gram. The chain is verified on the same route as AdaSpark's trees, laid out as a tree with one child per node, so that the two arms differ only in scheduling.
  • full-block chain: the drafter's whole block (9 picks for LFM2.5, 7 for Qwen3) verified as a chain.
  • fixed tree: a 16-row tree, best-first on the head-based estimate; no learned models.
  • cost model: the width chosen by Eq. (7) with the online cost model; acceptance from the head-based estimate; no n-gram.
  • AdaSpark: the cost model, the acceptance model and n-gram candidates together.

Our engine first verified a chain on its batch path for causal rows, whose attention does not split the keys across threadgroups as the tree path's does. At 8,444 tokens of context an 8-row chain then took 74.7 ms on Qwen3‑4B against 35.0 ms for an 8-row tree, and a comparison of AdaSpark with that chain would have credited the scheduler with a faster kernel. Moving the chain to the tree route leaves AdaSpark's text unchanged. The three-pick chain gives the same text on both routes in 10 of 11 replies of the short subset on each of LFM2.5‑2.6B and Qwen3‑4B; we expect, but have not traced, that each differing reply is a near tie that the key split's summation order resolves differently.

The autoregressive arms, the two DSpark arms and AdaSpark run on all four targets. The ablation arms run on LFM2.5‑2.6B and LFM2.5‑8B‑A1B, the dense and routed members of one family. The autoregressive arms measure only each engine's autoregressive speed, the denominator of its speedup over itself (Table 6); they run on a short subset fixed the same way: the first two turns of the first conversation of each source (11 timed replies). Table 9, Figure 7 to Figure 10 and §5.6 come from a separate, instrumented run of AdaSpark and the cost-model arm on the short subset with per-round logging on; the logging costs time, so those runs are not used for speed. Replies that reached the 8,192-token cap are left out of every statistic, per-round and per-request ones included, as they are out of the speed ratios.

The metric is decode speed on the client's clock: generated tokens over the time from the first to the last token of each reply. A reply that arrives as a single streamed delta, such as a bare tool call, has no such interval and is left out of the ratios. llama.cpp builds a tool-call parser from the Qwen3 chat template and refuses a request whose tool schema uses a type that JSON Schema does not define; ToolACE's schemas name Python's types, which the set builder renames (Table 5), so every engine serves every conversation. A comparison between two arms is the geometric mean over replies of the per-reply ratio. Replies within one conversation share their history and their arm's learned state, so they are not independent; the 95% interval is a percentile bootstrap that resamples whole conversations (2,000 resamples).

5 Results

5.1 End to end on four targets

On the evaluation subset (Table 6, Figure 6) AdaSpark decodes 1.89× faster than llama.cpp's DSpark on LFM2.5‑2.6B and 1.55× faster on LFM2.5‑8B‑A1B, 2.85× faster on Qwen3‑4B and 2.80× faster on Qwen3‑8B. With llama.cpp's own configuration, a chain of at most three draft tokens, imparo is 1.23×, 1.32×, 2.24× and 2.25× faster than llama.cpp on the four targets: this is the engine, with the algorithm held fixed. On the same engine and the same verify route AdaSpark is 1.53×, 1.17×, 1.27× and 1.24× faster than that configuration, over the same replies: this is the scheduler. Speculation is worth much more on the dense LFM2.5 target than on the routed one. Over each engine's own autoregressive speed, llama.cpp's DSpark is 1.55× on the dense target and AdaSpark 2.74×; on the routed target llama.cpp's DSpark is slower than its own autoregressive decode (0.80×), and AdaSpark is 1.16× faster than imparo's. On both Qwen3 targets the two engines' autoregressive decode is at parity (imparo 1.01× llama.cpp on both), yet llama.cpp's DSpark is slower than its own autoregressive decode (0.83× and 0.67×), while the same three-token chain in imparo is faster than imparo's (1.83× and 1.48×); we have not analysed llama.cpp's implementation to explain the difference. AdaSpark is 2.34× and 1.89× faster than imparo's autoregressive decode there.

On LFM2.5‑2.6B (Figure 7) the drafter's forward takes 9.7 ms and a 16-row verify 26.6 ms; a round commits 5.4 tokens on average, so a token costs 7.3 ms against 21.7 ms in autoregressive decode. On the routed target the drafter takes 7.2 ms and a verify of 6 rows, its most frequent width, 20.9 ms; a round commits 3.7 tokens, so a token costs 7.9 ms against 9.5 ms. Only about a billion of that target's eight billion parameters are read per token, so its autoregressive decode is fast, the drafter's fixed cost is a larger share of a round, and there is less for speculation to win. On Qwen3‑4B, whose drafter emits blocks of 7, the drafter takes 7.9 ms and an 8-row verify 26.4 ms; a round commits 3.6 tokens, so a token costs 10.0 ms against 23.2 ms in autoregressive decode. On Qwen3‑8B, which ran 8 rows in 98% of rounds, the drafter takes 11.2 ms and the verify 43.2 ms; its drafter's candidates are accepted less often (§5.3), a round commits 2.8 tokens, and a token costs 20.5 ms against 38.8 ms in autoregressive decode.

Held-out conversations. The 31 conversations (61 turns) of the test set outside the evaluation subset had not been run by any arm when the subset was measured. llama.cpp's DSpark and AdaSpark then ran on them (Table 7). AdaSpark's lead there is 1.82×, 1.49×, 2.87× and 2.76× on the four targets, against 1.89×, 1.55×, 2.85× and 2.80× on the evaluation subset: within 4% on every target, with overlapping intervals. Over the whole test set, 73 conversations and 153 to 161 replies per target, it is 1.86×, 1.52×, 2.86× and 2.78×.

5.2 Ablation

On the dense target (Table 8), verifying the drafter's whole block as a chain instead of three picks is worth 1.33×, a 16-row tree another 1.11×, and the cost model's width ties the fixed tree (1.000×, interval 0.992–1.006). The fixed arm is at 16 rows because our sweep (Table 3) found 16 rows best for this target; the cost model reached the same width on its own, in 76% of that arm's rounds on the instrumented run. The fitted acceptance model and n-gram candidates, added together, are worth 3.4% (interval 1.8–5.2%), 14.7% on LongBench and 7.1% on ConvFinQA, where the reply repeats its input; the n-gram candidates need the fitted model, since the head cannot price them (§3.3). On the routed target the order of the gains changes. The full-block chain is slower than the three-pick chain (1.28× against 1.32× over llama.cpp), because each extra row costs expert traffic; a fixed 16-row tree recovers little (1.35×); and the cost model's width, which on the instrumented run spread its rounds over widths of 2 to 16 rows (8 rows in 33% of them, 4 rows in 18%, 7 rows in 15%), is 11.2% faster than the fixed tree. The acceptance model and the n-gram candidates add 2.7% there (interval 1.3–4.3%).

5.3 What n-gram fill adds

On LFM2.5‑2.6B (Table 9), n-gram-only nodes hold 14.8% of the verified rows and supply 15.2% of the accepted draft tokens, and nodes both sources proposed supply another 18.6%. Agreement is strong evidence: an agreed node is accepted 72% of the time, against 25% for a node only the drafter proposed. N-gram-only nodes are accepted at 30%, against 25% for drafter-only nodes; their value is that they continue past the drafter's block when the text repeats. In 10.2% of the rounds that had n-gram candidates, those candidates moved the chooser to a wider class, and 65 of the 83 verifies of 24 rows or more were such widenings. On the routed target the shares are smaller: 10.2% of rows, 8.3% and 17.9% of accepted tokens, and 6.8% of rounds widened, because every extra row there costs expert traffic and the chooser buys fewer. By source, the n-gram's share of accepted tokens (n-gram-only and agreed together) runs from 7.7% on WildChat to 47.4% on LongBench on LFM2.5‑2.6B, and from 9.8% to 40.3% on the routed target. On Qwen3‑4B the n-gram contributes mostly through agreement: agreed nodes supply 19% of the accepted draft tokens and are accepted 65% of the time, while n-gram-only nodes are accepted 28% of the time, supply 4.7% of the accepted tokens and widen the verify in 2.8% of the rounds that had them. One reply of this run that looped to the 8,192-token cap is left out; inside it, n-gram-only nodes were accepted 84% of the time, which is why a loop is left out of every statistic. On Qwen3‑8B the drafter's own candidates are accepted least often (20%); n-gram-only nodes supply 12.7% of the accepted draft tokens and agreed nodes 22.6%, and they widened the verify in 4.0% of the rounds that had them.

5.4 By workload

The scheduler's gain is largest where the reply repeats its input (Table 10): on LFM2.5‑2.6B 1.73× on LongBench's documents and 1.70× on ConvFinQA's reports, against 1.43× on WildChat's open conversation. Against the fixed 16-row tree, which on this target is the best fixed width, the order is the same: 1.138× on LongBench, 1.083× on ConvFinQA and 1.013× on WildChat. On the routed target the gain varies less by source (1.13× on WildChat to 1.22× on ConvFinQA), because most of it comes from finding the target's width, which helps every source alike. On Qwen3‑4B the scheduler's gain runs from 1.22× on WildChat to 1.37× on ConvFinQA, and on Qwen3‑8B from 1.18× on ToolACE to 1.29× on ConvFinQA.

5.5 What the chooser picks

LFM2.5‑2.6B ran 16 rows in 84% of rounds and 12 rows in 5.5% (Figure 8), and Qwen3‑4B and Qwen3‑8B ran 8 rows in 97% and 98% of rounds. These are the widths the offline sweep of Table 3 finds best for these targets at medium and long context; the chooser reached them from an empty store, without that sweep. The wider verifies are rare and mostly follow long n-gram candidates (§5.3). The routed target has no such width. Its verify time rises with every row, and the chooser ran 2 to 7 rows in 70% of its rounds and 8 rows in 18%, moving between them from round to round; this is how it is faster than every fixed width in Table 3.

Table 11 compares the learned widths of §3.2 with the 8-bit matrix kernel's row classes, with the two arms alternating on the same engine. On the routed target, where time rises with every row, the learned table finds widths the kernel classes do not offer (2 to 6 rows, and 9) and is 4.1% faster, 5.2% at 443 tokens of context. On the 8-bit dense target it is 0.8% faster, 2.2% at 443 tokens. On the two Qwen3 targets it ties (+0.1% and +0.2%): 8 rows is the best width there at every context, and the kernel partition offers it. Every other AdaSpark result in this paper uses the learned widths.

5.6 Cost-model accuracy

From an empty store (Figure 9), the cost model on LFM2.5‑2.6B spends 34 rounds of the first request measuring widths, 1.5 s of its 16.7 s of decode, and 61 of the run's 1,684 rounds in all, as later splits add widths; over the second half of the run its estimate for the chosen width is within 1.3% of the measured verify time (median). On the routed target the first request spends 49 rounds and 1.8 s of 20.1 s measuring, but the median error is 6.8%. The difference is in the verifies, not the fit: an 8-row verify on the routed target varies with the experts its rows touch, and its median time is 6.9% above its 15th percentile, against 2.8% for a 16-row verify on the dense target. Part of that variation is real rather than interference, so the premise of Proposition 3 holds only in part there, and the low quantile prices the routed verify below its typical time. The gap is similar at 6 rows (6.6%), so the widths are still priced alike, and the chooser's widths on that target are faster than every fixed width (Table 3). On Qwen3‑4B the first request spends 41 rounds measuring, 2.2 s of its 30.7 s, and the median error over the second half is 1.3%; on Qwen3‑8B, 43 rounds, 4.9 s of 79.8 s, and 0.7%.

5.7 Acceptance calibration and agreement with plain decode

Over all rounds (Figure 10) the fitted model's expectation is within 1.5% of what was accepted on both LFM2.5 targets and within 2.5% on the two Qwen3 targets (realised over expected 1.005, 0.986, 0.978 and 0.985), and the head-based estimate is within 1% on LFM2.5‑2.6B (1.005): in aggregate both are calibrated. Binned by S, every series lies above the diagonal at small S and below it at large S: the models under-state what their least confident trees accept and over-state what their most confident ones accept. This compression is why the chooser rescales the expected gain of extra rows by a fitted factor (§3.4) rather than taking S at face value. The fitted model's advantage is per node, which is what the order and the width depend on: its log loss is 12.3% lower than the head-based estimate's on LFM2.5‑2.6B, 10.4% lower on the routed target, 14.9% lower on Qwen3‑4B and 14.0% lower on Qwen3‑8B, and it is lower on 91 of 91, 94 of 94, 87 of 87 and 93 of 93 requests after the first (Table 2, Figure 4).

On the evaluation subset, 82 of AdaSpark's 95 replies on LFM2.5‑2.6B are byte-identical to imparo's three-pick DSpark, 39 of the 42 first turns (Table 12); on the routed target 75 and 34, on Qwen3‑4B 80 and 37, and on Qwen3‑8B 78 and 36. Every emitted token is the target's argmax on its verify row (§3.5); we expect the differences to come from near ties that verifies of different widths resolve differently, since a verify's rows are width-invariant only within one accumulation order of the matrix kernels (§8). The routed target's choice of four experts per layer is a further point where a near tie can change the computation, but we have not traced the individual divergences. Once a reply differs, the rest of its conversation differs too, since each arm carries its own replies as history.

6 Discussion

Why learn online. The measurements show three sources of variation in the quantities a width decision needs. The verify's time depends on the target and its weight format (Figure 3): the same machine and kernel library give a nearly flat 16-row class on one target and a 50% step at the 9th row on another. Each class's time depends on context, with its own slope (Table 1). And what a wider tree buys depends on the text being generated (Table 10). A profile taken before serving can capture the first two, but only for the model file, quantisation, device and kernel build it was taken on, and it must be retaken whenever any of them changes. The third changes while serving, with the workload. AdaSpark needs none of this in advance: its cost model starts from a ladder of six widths and its acceptance model from a prior derived from the features' definitions, and the only price is a cold start of 34 to 49 rounds in the first request, 6–9% of its decode time.

Two learners, two clocks. The two quantities change for different reasons, and that is why AdaSpark fits them with two models rather than one. The verify's time is a property of the model file, the device, the kernels and the context: it does not change while a model is served, so the cost model converges once per model and device, is stored, and afterwards tracks only the context and the machine's drift (§3.2). Acceptance is a property of the text: it changes with every request and whenever the workload changes, so the acceptance model keeps learning, carries a per-request term that adapts within a reply (§3.3), and is the part that must recover quickly after a switch. At the 20 changes of source in the evaluation run (five per target), the fitted model's advantage over the head-based estimate on the first request of a new source is typical of that source: it ranks 0.42 on average among the source's requests and falls below their median at 9 of the 20 (Figure 4). What differs most between workloads, the n-gram evidence and the context, enters the model as features rather than as something it must relearn, and the per-request term starts afresh with every request; no detector of workload changes was needed on these workloads. Fitting both with one learner would force one rate on both: either the cost would be re-learned from noise every request, or acceptance would lag a workload change by as long as the cost takes to converge.

Engine and scheduler. The mix of the two factors depends on the target (Figure 6). On the Qwen3 targets most of the gain over llama.cpp is in the engine's speculative path, since the two engines' autoregressive decode is at parity there. The scheduler's share is largest on the dense target whose verify is nearly flat to 16 rows, where a wide tree costs little and n-gram candidates are cheap to carry, and smallest on the routed target, where every row costs expert traffic. The two Qwen3 targets sit between them: their 4-bit verify steps at the 9th row, so the chooser stays at 8 rows.

Against the best fixed width. We compare with a fixed width tuned by a sweep. Such a width exists only after the sweep, which has to be repeated for every target, context range and weight format; AdaSpark reaches the same width without one. Where one width is right in almost every round, as on the dense LFM2.5 target at 1,596 and 8,444 tokens and on both Qwen3 targets at every context, a tie with the sweep is the expected result: on the three dense targets AdaSpark's width is within 1.1% of it in every cell and faster in seven of the nine. Where the right width changes from round to round, as on the routed target, the chosen width is faster than the best fixed tree at every context, by 0.6–4.2%. A wrong fixed width is expensive: on the routed target the cost model's width is 11.2% faster than 16 rows, the best fixed width on the dense target (§5.2).

7 Related work

Table 13 summarises how schedulers for speculative decoding size a verify: whether the size is chosen anew for each verify, and where the two quantities the choice needs come from.

Tree size from a cost. CAST [1] sizes a speculative tree from a latency table over batch size, context and tokens fed, measured per device before serving, with thresholds set by hand per model. Sequoia [8] also profiles the hardware to size trees, and CaDDTree [11] sizes diffusion draft trees from a cost curve fitted offline once per model and device. DDTree [10] builds draft trees from a block-diffusion drafter. Three recent schedulers choose the tree size each round from a cost and the prefix property of Proposition 1: two by the ratio of expected accepted tokens to cost, one by a price per verified token. EVICT [39] does this for EAGLE-3 trees on mixture-of-experts targets, with acceptance from the draft probabilities and a step-latency table profiled at initialisation for each verify length, with no context term. Bastion [40] does it for block-diffusion drafters, with a roofline model in width and context that is calibrated offline per GPU and target and can be corrected online by one multiplicative factor; its stopping rule assumes the cost is convex in the width. TreeSpark [41] builds DSpark trees from parent-conditioned candidates and stops at a price read from a latency ladder measured once per deployment. TurboSpec [52] and ASPIRE [53] fit linear cost models offline, and D-cut [65] prunes verify depth from a cost table profiled at startup. Cascade [48] measures the utility of a few draft lengths online in short test phases, without a cost model, and AdaptiveSD [2], BanditSpec [13] and Sun et al. [54] learn a chain's length online from measured outcomes. Other tree methods fix the budget: PCTree [42] at a size found by a sweep, Trees from Marginals [61] likewise, and TALON [45], ECHO [47] and Graft [43] at fixed budgets with thresholds set in a warm-up run. EAGLE-2 [35] and OPT-Tree [36] select a dynamic tree's nodes by the product of draft probabilities along the path, the rule of Proposition 1, with a fixed node budget. AdaSpark differs from all of these in fitting the verify cost while serving, for widths it learns and as a function of context, with no profile or calibration taken before serving, and in pricing time at the long-run rate over a cost with steps.

DSpark in serving engines. vLLM [37] and SGLang [38] each ship a scheduler for DSpark, and Table 14 compares them with AdaSpark. Both size a batch-wide verify budget by the ratio of expected accepted tokens to the cost of a step, and both take expected acceptance from the drafter's confidence head. vLLM's adaptive verification (enable_adaptive_verification, off by default) profiles its table at startup at one context length, 8,192 tokens by default, and passes it through a running maximum that makes it monotone by construction; its table is a step function because CUDA-graph capture pads a batch to the next captured size. SGLang's scheduler reads a table written by a separate offline profiler, which by default decodes 16-token prompts for about 570 steps, so its contexts stay below about 600 tokens; without that file the scheduler verifies every drafted token. Neither refits its table while serving.

Predicting acceptance. SpecDec++ [12] trains an acceptance-prediction head onto the draft model and stops drafting when the predicted probability of a rejection crosses a threshold. DSpark [3] trains its confidence head on the per-position acceptance rate, calibrates it offline by temperature scaling, and passes the calibrated values to its scheduler. TreeSpark [41] reports that this head ranks tree edges poorly and replaces it with a two-parameter map from the drafter's probability, fitted once to the target's outcomes; TAPS [46] trains a scorer over each parent's children offline from recorded verifications; C2T [55] trains a classifier on accepted and rejected tree nodes; and LiLiCorr [60] trains a head on the drafter's confidence features. TurboSpec [52] and ASPIRE [53] track an acceptance rate online as a running average, and BanditSpec [13] learns the draft length online as a bandit problem. D-PACE [9] trains a parallel drafter with a loss that weights positions by the draft's confidence. Our measurements (§3.3, Table 2) agree with TreeSpark's that a model fitted to the target's outcomes predicts acceptance better than the head. AdaSpark fits a per-node model of that kind online, from an empty store, with separate terms for n-gram candidates and for agreement between the two sources.

Text-derived candidates. Prompt lookup decoding [29] matches n-grams against the prompt, REST [30] retrieves continuations from a datastore, ANPD [14] adapts the n-gram order online, the N-Grammys [15] batch several learning-free proposers, PLD+ [16] and LogitSpec [17] refine which candidate to take, and SuffixDecoding [56] and SAM Decoding [57] match suffixes of the prompt and of earlier outputs. These methods either use the text as their only source or switch between a text source and a model drafter at each step: SuffixDecoding's hybrid mode and Arctic Inference [63] take the suffix draft when its score passes a threshold, TensorRT-LLM [64] lets a suffix-automaton draft override the neural one above a match length, SAM Decoding selects by match length, and a probe on the target's hidden states makes the choice in [58]. DART [59] uses an n-gram model built offline to rerank a drafter's candidates without adding its own. Two methods verify a model drafter's candidates and retrieved candidates in one tree. RASD [44] merges an EAGLE-2 tree with a retrieval tree for one verify. Graft [43] prunes an EAGLE-3 tree at confidence checkpoints and fills the freed slots of a fixed 60-node budget with continuations from a token-successor table, following a fixed template per stage. Both divide the rows between the sources by fixed rules. In AdaSpark one fitted acceptance model prices both sources and they compete for rows in one best-first order, so an n-gram candidate takes a row only from a candidate the model ranks below it, and n-gram candidates widen the verify only when the cost model says their expected tokens pay for it. SpecInfer [18] merges the token trees of several small draft models into one verify. Among the serving engines, llama.cpp uses the first speculator that returns a draft in each round, and the released versions of vLLM and SGLang construct one proposer per server.

Verify cost on mixture-of-experts targets. MoESD [49] models the verify cost of a mixture-of-experts target by the expected number of distinct experts the verified tokens activate. Cascade [48] measures verify time growing two- to three-fold with the draft length and chooses the length online by its utility, EVICT [39] motivates its truncation by the same growth, MoE-Spec [50] budgets the experts a verify loads, and [62] bounds the speculation budget offline with an oracle. Our routed target shows the same growth from 2 to 16 rows; what we add is its effect on the width choice next to dense targets on the same kernels, where the best width differs (§3.4).

Other work on block drafters. Work on the drafter itself is complementary to a scheduler: DeLS-Spec [69] separates long and short context in the drafter, [66] analyses what a block drafter can and cannot predict at each position, Carryover Drafting [67] reuses the states of rejected drafts, and [68] runs the drafter's forward pass concurrently with the verify, which would shrink AdaSpark's fixed per-round cost D.

8 Limitations

One machine. All measurements are from one machine and one backend. The positions of the steps in §3.2 follow from the kernel geometries the tuner picks on this device; we expect the shape (nearly flat classes, steps, per-class slopes in context) to transfer and the breakpoints not to, but have not verified this on a second device. The widths themselves are learned (§3.2), so they move with the kernels rather than with what the backend declares.

Constants. Every constant was set while developing on LFM2.5‑2.6B and is used unchanged on the other targets (Table 16); only the hysteresis margin and the exploration period were chosen by comparing values, the rest from what each quantity means.

Width invariance. The width invariance that Proposition 5 and the gain estimates rely on holds only within one accumulation order of the matrix kernels (widths 3 to 16, or 3 to 24 on the 8-bit target). The rounds that ran wider, up to 4% of them, sit outside it, and so do the 2-row verifies, which run a one-row kernel: 8.5% of the rounds on the routed target.

Routed targets. On the mixture-of-experts target the verify's time also varies with the experts a round's rows touch, which is real variation rather than interference; the low-quantile price then sits about 7% below the typical verify (§5.6). The gap is similar at the widths the chooser weighs against each other (6.6% at 6 rows, 6.9% at 8), so they are still ranked correctly, but we have measured this on one routed target only.

Greedy decoding. Every run decodes greedily, which the verifier requires as built. Under sampling a candidate is accepted with a probability rather than by equality, which is the setting the confidence head was trained for (§3.3) and would change what the acceptance model's labels mean; we have not evaluated it.

Serving. The end-to-end runs serve one request at a time. With concurrent requests the verify batch is shared and the time of a width depends on what else is batched, which the cost model does not represent.

Statistics. Each arm serves the evaluation subset once, in a fixed order, so arm-to-arm comparisons include any drift of the machine over the run. The machine slept for an hour during its three-token chain arm; the five replies of the one conversation that spanned the sleep were run again on the same binary, with byte-identical text, and the new timings replace the old. Replies within a conversation are not independent, and the intervals resample whole conversations: 42 on the evaluation subset, 31 held out, and between 4 and 13 per source, so the per-source cells are less certain than the totals. The speedups over autoregressive decode divide speeds measured on different replies and carry no interval. Table 3 reports means with no interval. One 256-token run of one prompt differs between its two passes by 0.07% in the median over the cells of Table 3, by 1.8% at the 90th percentile and by up to 5.4% (12 rows on LFM2.5‑2.6B, one prompt at 8,444 tokens), so differences of 1–2% between its cells are within that spread.

Baseline. Speedups are reported against llama.cpp's DSpark at its default draft length of three. We did not tune the baseline, and a different draft length could change its numbers; the full-block chain arm shows what a longer chain does in our engine. The schedulers of §7 that choose a tree size from a cost, and the DSpark schedulers of vLLM and SGLang, run on CUDA; we did not port them to this engine, so they are compared with AdaSpark by design (Table 14) rather than by measurement. The nearest measured stand-in is the fixed width that an offline sweep finds best (§3.4).

9 Conclusion

The time a tree verify takes is not a smooth function of its width. On the kernels we measured it is a step function whose steps depend on the target and its weight format, each class's time grows with context at its own rate, and on a mixture-of-experts target the time rises with every row over the widths we measured. What a wider tree buys depends on the drafter, the target and the text being generated. A fixed width, or a width read from a table profiled before serving, fixes these quantities in advance.

AdaSpark fits both quantities from the rounds it serves: the widths worth offering and a low-quantile law in context for each one's verify time, and a multinomial over each parent's children for acceptance. The same acceptance model prices n-gram continuations of the request, so they can join the drafter's tree and take rows only when they are worth them. Starting from an empty store, with constants set once on one target, it reaches the width that a sweep finds best on each dense target, and on the routed target, where the best width changes from round to round, it is faster than the best fixed tree at every context. Against llama.cpp's DSpark with the same drafter files it decodes 1.52× to 2.86× faster over the whole test set; with the engine held fixed, the scheduler alone contributes 1.17× to 1.53×. The questions it leaves open are those of §8: a second device, sampling rather than greedy decoding, and verify batches shared between concurrent requests.

Appendix A Engine, targets and hardware

AdaSpark is implemented in imparo, an inference engine with Metal and CUDA backends. A verify is one batched forward over the tree's nodes, with a per-row ancestor mask in attention; the widest verify it runs is 64 rows. The two LFM2.5 targets are hybrids whose blocks mix attention with a short convolution. A tree over such a layer needs per-row convolution state rather than a mask, and the engine carries it.

All measurements were taken on one Apple M3 Pro (12 CPU cores, 18 GPU cores, 36 GB of unified memory with 150 GB/s nominal bandwidth, macOS 15.7.9) with imparo's Metal backend. The step boundaries in particular are a property of that machine's kernels; §8 discusses what should and should not transfer.

The llama.cpp baseline (§4.1) is build 11201, commit 2145525a4, run on the same machine with the same GGUF files.

Appendix B Reproduction

The test set, its builder, the harness and the scripts that produce every table and figure are in the dspark-paper/ directory of the engine's repository. testset/build.py rebuilds the conversation sets from the pinned source revisions and testset/context.py rebuilds the microbenchmark prompts. harness/run.sh runs, per target, the short subset with every arm, which must pass automatic checks; then the speculative arms on the evaluation subset, which must pass the same checks; then the width table (Table 3), the cost survey (Table 1, Figure 3) and the instrumented run for the figures. harness/run_chain.sh and harness/run_learned.sh measure the chain arms and the arms that run the cost model, whose rows are the ones reported for those arms, and harness/run_heldout.sh and harness/run_toolace.sh run the held-out and the ToolACE conversations. Each run log records the checksums of the binaries it ran, and the harness reuses a completed stage only if it was measured on the same server binary. On LFM2.5‑2.6B the chosen column of Table 3 was measured a second time with nothing else running, because three of its nine cells differed between passes by more than 5%; no other target's did.

The ToolACE conversations were run by every arm of the evaluation run, over all eight in one run per arm, and those rows replace every arm's rows of the six conversations whose schemas the type rename of Table 5 changed. Each arm of that run starts from an empty store and serves ToolACE first, where in the evaluation run it had already served four other sources. On the two conversations the rename did not change, AdaSpark ran 2–6% slower in that run than in the evaluation run, and llama.cpp's DSpark within 0.3% on three targets and 6% faster on LFM2.5‑2.6B; we did not test the store as the cause, but the replaced rows, if anything, understate AdaSpark.

The kernel-class arm of Table 11 is not part of the released engine, which learns its widths only. The width-invariance check of §3.5 is imparo-forward --decode-vs-verify (docs/evidence/dspark/2026-09-28-width-invariance.md).
